## 1. What Fuzzies is

**Fuzzies** — tagline **"Dream it fuzzy. Make it sharp."** — is a Canva-style design app for phones and computers,
with a built-in Frogger-style game, **Fuzzy Crossing**. In the game you collect **Fuzzies** (tokens) that unlock
premium templates, graphics, stickers, fonts, text effects, app themes and game skins. The owner's goals:
super professional *and* easy to use, lots of creative freedom, easy sharing/saving, and "cute stuff" that
keeps people coming back (the mascot, the game, missions).

- **Repo:** https://github.com/ykob14/fuzzies. (note the trailing dot in the repo name) — `main` is the live branch.
- **Owner:** GitHub `ykob14`. Not a developer: explain things in plain words, show screenshots, keep replies short.
- An older, outdated copy lives in the `fuzzies/` folder of `ykob14/cap-off` (branch `claude/fuzzies-design-app-jwv4tu`). **Ignore it** — this repo is the source of truth.

## 4. How to run, build and test

```bash
npm ci
npm run dev        # http://localhost:5173 (also on LAN for phones)
npm run build      # tsc --noEmit + vite build → dist/
npm run preview    # serve dist/
```

- There is **no automated test suite** yet. Verification so far = `npm run build` + scripted Playwright runs.
- **Playwright in a cloud container:** Chromium is at `/opt/pw-browsers`; launch with
  `args: ['--enable-unsafe-swiftshader','--use-angle=swiftshader','--ignore-gpu-blocklist']` for WebGL.
  Software WebGL runs the 3D game at ~1 fps, so step the game/intro manually rather than waiting in real time
  (e.g. import `/src/game/view3d.ts` from the Vite dev server and call `view.render(game, dt)` yourself).
- Animated elements (the mascot) never become "stable": take screenshots with `page.screenshot({ clip })`, not `element.screenshot()`.
- **QR codes** were verified by decoding with `jsqr` (installed in a scratch folder, not a project dependency) — versions 1–10 and an exported PNG all decode.
- **Backend testing:** any Postgres works. Set `DATABASE_URL=postgresql://user:pass@127.0.0.1:5432/db` and run `npm run dev`
  (Vite serves `/api/*` with the real functions, tables auto-create). In the cloud container Docker works once the daemon
  is started (`sudo dockerd &`); Docker Hub may rate-limit pulls. Use two Playwright browser contexts as two devices and
  poke `/src/core/*.ts` modules via `page.evaluate(import(...))`. `npx vercel build` (CLI in a scratch folder, with a fake
  `.vercel/project.json`) checks that Vercel can build the functions; the built `.vercel/output/functions/api/*.func/api/*.js`
  can be imported in Node and called with a `Request`.
- **Test gotcha:** if you edit a module while Vite is running, a test's `import('/src/…')` can load a *second copy* of it
  (the app's copy has a `?t=` stamp). Restart Vite before tests that poke at module state.

## 5. Tech & architecture

TypeScript + Vite, **no UI framework** (small `h()` DOM helper in `src/ui/dom.ts`). Three.js only for the game's
3D view and the mascot renders (lazy-loaded chunk). Data is **on-device first**. The **backend** is a pair of Vercel
functions in `api/` using a **Neon Postgres** database (`pg` driver); it adds real accounts and sync. Cloud mode switches
on at build time when `DATABASE_URL` exists (see `BACKEND.md`); without it the app is exactly the on-device version.

## 6. Rules of the codebase (gotchas)

- **Adding an account field:** add it to the `Account` type *and* to `fresh()` in `core/account.ts`; `migrate()`
  merges defaults into old saved accounts (nested objects need their own spread in `migrate()`). It syncs automatically
  (the whole account goes to the cloud minus `hash/salt/id/email/cloud/guest`). If it's a **counter**, `merge.ts` adds both
  devices' changes; if bigger-is-better (like a best score) add its key to `MAX_KEYS`; lists are unioned.
- **Cloud sync:** always write designs/uploads through `db.*` (the sync hooks there). Writes that came *from* the cloud
  pass `quiet = true`. Account changes go through `accounts.update()` as before. `accounts.store()` saves without notifying the queue's
  "changed" check (used for cloud copies). Never put `DATABASE_URL`/`AUTH_SECRET` in the app or repo (only the yes/no
  `__CLOUD__` flag reaches the browser). API errors shown to people come from `HttpError` messages only.
- **Design documents:** every load path goes through `migrateDesign()` (`editor/model.ts`): opening in the editor, .fuzzies import,
  share links, template instantiation. It is idempotent and never throws away content. If you change the format, bump `DOC_VERSION`,
  add the upgrade step there and keep old fields readable. Templates are copied by `instantiate(src, owner, name, templateId)` — never edited.
  Layer order = array order (index 0 = back); groups are flat (`group` id). `folder` is a My Designs label (syncs with the design).
- **Editor saving:** call `commit()` after a change (undo step + autosave). Saves are serialized in `persist()`; `saveNow()` is used
  for Ctrl/Cmd+S and tab hide/close. The status chip (`setStatus`) shows Saving / Saved / Not saved · Retry.
- **Editor rendering:** while moving/resizing/rotating, `dragLayers()` caches the layers below/above the selection; pan/zoom gestures use
  `gesturePicture()`. Anything that changes pixels *during* a drag must be part of the selection or it won't show until the drag ends.
  Editor view prefs (grid on/snap/size) live in `localStorage` `fz.ed.view`; the inspector open state in `fz.ed.inspector`.
- **Adding an element type:** update `types.ts` (El union), `render.ts` (`drawElement`), `doc.ts` (factory + `elLabel`),
  `props.ts` (title map + section), `panels.ts` (add button + `layerIcon`). TypeScript catches most misses.
- **Fonts:** every weight listed in `content/fonts.ts` must really exist on Google Fonts, or the whole CSS request fails.
- **Game:** rules live in `crossing.ts`; views only draw. New visual effects = new `Fx` events → `view.fx()`.
  Objects wrap `OFFSCREEN` cells past the edges so they never pop in.
- **Fuzzies Land:** the town lives in `account.land` (synced; merge keeps the most recently saved town whole). The screen
  works on a copy and saves after every action (`save()`) and on hide/pagehide/leave; rules functions throw `Error`s with
  friendly messages. Everything timed is a wall-clock timestamp (`crop.at`, `queue[].end`, `doneAt`) so progress continues
  while the app is closed. Don't rebuild HUD/panel DOM on a timer (taps get lost) — update text in place.
  New buildings/goods = add to `ITEMS`/`GOODS` in `land/rules.ts` + a model in `land/models.ts` (`modelFor`).
  In dev, `window.__land = { view, state }` lets tests step frames (`view.stop(); view.frame(0.05)`).
  **Art:** follow `ART.md` (palette `PAL` in `land/models.ts`, `PALETTE` in `land/environment.ts`; build new buildings from
  the helpers `plinth`, `gableRoof`, `windowOn`, `doorOn`, `cornerTrims`, `chimney`, `bush`). Land is **full screen** (the router
  renders it without the app shell) with its own fixed cream UI tokens (`--lc`, `--link`, `--lacc`… on `.page.land`, which
  also overrides `--surface`/`--text` so panels look the same in dark mode). Shop cards show 3D pictures from
  `view.thumbnail(itemId)` (rendered once into a corner of the canvas, cached as PNG data URLs).

- **Photo frames:** checked with emulated touch in Chromium — iOS Safari's own picker behaviour needs the owner's iPhone (the picker opens from the tap's `click` event, which iOS allows). A tap on an empty frame always opens the picker (drag it to move it instead; cancel the picker to just select it). A filled photo can be re-cropped only through the inspector's pan/zoom.
- **Team templates (Residence Life and the rest of `team.ts`):** photo slots are placeholders (tap the frame to add a photo); names/roles are separate text layers, so a longer name shrinks only when edited by hand. Six cards per page in the 6-person layouts (duplicate or delete a card's layers for more/fewer RAs).
- **Brawl Arena:** played by bots and in the software-rendered test browser (~1 fps) — the real feel of the thumb sticks, aim assist and frame rate on a phone (six GLB Fuzzies + kit props + bolts) needs the owner's hands. The computer Fuzzies are rule-based (no learning); difficulty is a fixed skill per Fuzzy (allies 0.58–0.62, opponents 0.60–0.68 in `brawlView.ts`). The GLB Fuzzy's face can't show expressions, so hits/KOs are motion + effects. One map, one mode (by the owner's order). Score bounds aren't checked by the server (like the other games).
- **Phone fixes (Balloon Pop, page lock):** checked in Chromium with emulated touch only — iOS Safari's own page bounce can't be reproduced here, so the owner's iPhone is the real check. Tiers for Balloon Pop were retuned by bots after the 9-balloon cap.
- **Obstacle Run:** the joystick in Fruit Catcher / Fishing (`controls.touch: false`) still listens to touches (the kit's `mountControls` ignores `touch: false`); Obstacle Run and Brawl read touches first and stop them — the shared fix waits for a session that can retest those two games.
- **Real models:** only Fruit Catcher uses them so far; the town and the other 16 games still use the old art. **Never redesign the Fuzzy** — the owner wants their model as is (blend it with light, shadow, size and motion only). Kits are fetched on first play (2.4 MB on phones, no offline cache yet). Blender + gltf-transform are needed only to rebuild kits (not part of `npm run build`). The KayKit Restaurant pack is fetched but not used yet.
- **Art pass (all games):** seen only in software-rendered screenshots — real-phone frame rate with shadows now on in every mini-game is the big unknown (first things to trim: the tree line's leaf cards, grass tufts, phone shadow map). The Forest's game trees are still the town's own smooth trees (the tree line around them uses the new leafy style). The Boat Race island ground is still vertex-coloured (no painted texture). Faded trees/palms swap material instantly in the Forest (no fade-in).
- **Fruit Catcher art pass:** reviewed in software rendering only; real-phone frame rate with shadows on phones is unmeasured (phones use a
  1024 shadow map, ~90 leaf cards per front tree, ~230 instanced tufts — first things to trim if it stutters). The GLB Fuzzy still has a
  baked face (no blinks / smiles on catches); the drawn Fuzzy is used when Deluxe is off. Portrait phones play a narrower lane (≈3.5 m
  half-width vs 7 m) so the same tiers are a little easier there. The other 16 games keep their primitive look until they get the same
  treatment; `orchardArt.ts` covers farm/orchard scenes (harvest, garden, delivery could reuse it directly).
- **20-game adventure system:** 17 of the 20 games are playable; **Kart Race, Dolphin Adventure and Fuzzy Cooking are "coming soon"**
  (never drawn into a set). Every new game was played by bots in Node and in the software-rendered test browser (~1 fps) on emulated
  computer + phone layouts — the feel of the joystick, tap-to-walk, the skating slide and the frame rate on a real phone still need the
  owner's hands. Tiers were calibrated by bots, not people (retune `SCORING.tiers` per game and the matching words in `adventures.ts`
  together). The server validates sets, days, places and "already paid", not scores (a technical user could claim a better tier). Rivals
  exist only in the Forest Challenge and the Boat Race; the other games are solo score runs. Guest/on-device accounts issue their own sets
  from the device clock (cloud accounts use the server's). Scenes are built from cheap meshes but 17 scenes' worth of chrome has not been
  profiled on a low-end phone; the kit steps shadows/pixel ratio down like the race.
- **Owner's 3D Fuzzy / Fuzzy Friends:** the model is one baked mesh (29k triangles, one texture) — it can't blink, wink, talk or
  move its eyes, so the brand mascot and the Fuzzy helper still use the drawn Fuzzy, and deluxe residents express themselves with
  body motion only. Fur colours per Fuzzy come from a hue shift of the pink texture (a very dark or grey skin looks muted). The
  1.5 MB file loads once per visit (not pre-cached by the service worker); on a slow connection the first town/game/race may show
  the drawn Fuzzies until it arrives. Phone frame rate with 8+ model residents hasn't been measured on a real device (the
  Settings switch is the fallback). The friends were cut out by flood-fill from the sheet: a few edges keep a thin light halo
  on dark backgrounds.
- **Daily mini-games:** the vacuum and forest were played in a software-rendered test browser (~1 fps) and by bots in Node — the feel of the joystick, tap-to-walk and frame rate on a real phone still need the owner's hands. Forest rivals are simple: they walk straight at their tree (slipping round trunks), pass through each other and through you, never pick up wood pieces (their wood is counted straight in) and don't talk; their difficulty is three fixed skills (retune in `land.ts` / `SCORING.rival`). Towns with fewer than three Fuzzies get fewer rivals. The once-a-day rule is enforced by the screens (the rules still accept a practice run, paying nothing). The Forest's wood only matters as score + barn count (nothing spends it yet). No leaderboards (personal bests only). The server claim checks place/day, not scores.
- **Fuzzies Adventures / Boat Race:** played in a software-rendered test browser (~1 fps) and the rules in Node — the real feel of steering,
  the 60 fps target and phone performance need a real device (the race drops pixel density/shadows by itself when slow; the new scene adds
  ~50 boundary buoys, 12 hazards, fish/birds/dolphins — all cheap meshes, one instanced fish mesh). The GLB riders have no face animation
  (the drawn Fuzzies get the pupil/mouth reactions). Dolphins and fish are decoration (no collisions). Boat-vs-boat contact is still a simple
  circle bump; a proper axe-chop animation for the forest Fuzzy is still to do. Only 2 of 7 adventures are playable (the others are listed as coming soon). Rewards are town coins/XP
